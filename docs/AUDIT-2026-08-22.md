## 버그

### B-1. CAT 탭 대사가 사용자의 접속 시간을 안다고 주장함

- 재현: 관계도 20의 CAT 계정에서 접수대 고양이를 실제로 반복 탭했다. 슬립에 `올 시간은 알고 있었다냥. 기다린 건 아니다냥.`이 노출됐다.
- 근거: 해당 문장은 관계 2단계 탭 풀에 직접 들어 있다. `app.js:3251`, `app.js:3253`
- 문제: 사용자가 입력한 적 없는 접속 시간 패턴을 집사가 안다고 말한다. 실제 추론 함수가 없어도 문장 자체가 감시처럼 읽힌다.
- LOCKED 충돌: `docs/CURRENT.md:65`, `docs/CURRENT.md:67`, `docs/HANDOVER.md:116`, `docs/HANDOVER.md:118`
- 수정 방향: 시간 예측을 없애고 서류/자리/집사 자신의 기다림만 말하게 한다. 예: `주인님 자리만 정리해뒀다냥. 기다린 건 아니다냥.`

### B-2. legacy 인증서가 있으면 공식 인정 수와 다음 발급 안내가 동시에 모순됨

- 재현: `tests/personnel-migration.html` fixture를 실행하고 누락된 주인님 호칭을 등록한 뒤 파일 탭을 열었다.
- 관찰: 기록 4건 모두 `공식 인정` 도장이 붙고 표지는 `공식 인정 4건`이라고 표시했다. 바로 아래 안내는 `5건이 모이면 ... 발급합니다. (1건 남음)`이라고 표시했다.
- 원인: legacy `achievements`에 `isCertificate: true`가 4개 들어 있다. migration은 `isCertificate !== false`인 legacy 항목 전부를 `state.certificates`로 옮기지만, 다음 발급 진행도는 별도로 유효 기록 수 5/7 규칙만 계산한다.
- 근거: `tests/personnel-migration.html:6`, `tests/personnel-migration.html:15`, `app.js:1135`, `app.js:1139`, `app.js:1141`, `app.js:1840`, `app.js:1846`, `app.js:2299`
- 영향: legacy 사용자는 아직 첫 공식 인정 전이라는 안내와 이미 받은 공식 인정 여러 장을 동시에 본다. 이후 인증서 회차 숫자도 `state.certificates` 순서에 의존해 과거 의미와 어긋날 수 있다. `app.js:1859`, `app.js:1865`
- LOCKED 충돌: 기존 사용자 데이터 보존, 공식 인정 인증서 단일 계보, 5건 이후 7건 주기 규칙과 충돌한다.
- 수정 방향: legacy 증서를 삭제하지 말고, 구형 기념 증서와 신형 공식 인정 milestone의 의미를 migration에서 분리하거나 유효 기록 순서에 맞는 milestone만 공식 인정으로 이관한다. 데이터 의미 결정은 오너 판단이 필요하다.

### B-3. 선물만으로 관계가 오른 계정에 존재하지 않는 기록 습관을 지어냄

- 재현: 기록 0건, 선물 18개, 관계도 65인 CAT 계정을 만들고 집사 탭을 열었다.
- 관찰: 관계 카드에 `선물만 주인님이 자주 적는 칸은 미리 펴 둔다냥. 편의가 아니라 효율이다냥.`이 표시됐다.
- 원인: 관계는 선물로도 오르지만 관계 단계 대사는 입력 기록 유무와 무관하게 고정 선택된다. `app.js:633`, `app.js:639`, `app.js:2097`, `app.js:5496`, `app.js:5501`
- 문제: 사용자가 한 번도 기록하지 않았는데 `자주 적는 칸`이 있다고 주장한다. 감시 계산은 아니지만 사용자가 말하지 않은 생활/기록 패턴을 만들어낸다.
- LOCKED 충돌: 집사는 사용자가 직접 입력한 내용만 알며, 관계 성장은 애정이 새는 방식이어야 한다는 규칙과 충돌한다.
- 수정 방향: 관계 시스템 리팩터링 없이 이 단계 CAT 문장을 기록 유무와 무관한 애착 표현으로 바꾼다. 예: `주인님 파일은 미리 펴 둔다냥. 편의가 아니라 효율이다냥.`

## 사소

### S-1. 중복 접수 규칙과 파일 안내문이 서로 다르게 말함

- 재현: `씻었어`를 두 번 접수하면 카드가 `x2`로 접히고 두 번째 기록은 도장에 반영되지 않았다. 동작은 LOCKED와 일치했다.
- 관찰: 같은 파일 화면 안내는 `모든 기록은 대업 후보로 접수됩니다.`라고 말한다. 실제로는 모든 기록이 보존되지만 중복 기록은 후보/도장 대상이 아니다.
- 근거: `app.js:2300`, 상세 상태 구분 `app.js:2872`
- 수정 방향: `모든 이야기는 기록되며, 유효 대업 5건이 모이면...`처럼 보존과 도장 자격을 분리한다.
- LOCKED 충돌: 현재 문구가 중복 재접수 LOCKED 규칙과 어긋난다.

### S-2. `누적 명성` 값에 `건` 단위를 붙임

- 관찰: 파일 하단 요약에서 `누적 명성 6건`으로 표시된다. 같은 화면에서 기록과 공식 인정은 건수지만 명성은 수치라 단위가 맞지 않는다.
- 근거: `index.html:324`
- 수정 방향: `누적 명성 6` 또는 제품에서 사용하는 명성 단위로 통일한다.
